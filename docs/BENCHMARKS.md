# NebulaOS benchmarks

Generated by `nebula bench` on 2026-10-25 00:53 IST (darwin/arm64, 8 CPUs).

Every number below comes from a real cluster of **5 separate OS processes** talking gRPC over loopback, with Raft writes fsynced to disk (`--fsync=true`). Failures are `SIGKILL`s — no graceful shutdown. Workloads use the `sim` runtime so the measurements isolate the control plane from image pull and container start time.

Timers: heartbeat 300ms, node timeout 2s, Raft election timeout 500ms–1s.

## Failure recovery

Each scenario ran 5 times from a fully healthy cluster. *Recovery* is wall-clock time from the `SIGKILL` until every replica of every service is reported running again. *Availability* is the mean fraction of desired replicas running over the 15 s after the kill.

| Scenario | New leader (median) | Failure detected (median) | Recovery median | Recovery worst | Replicas moved | Availability |
|---|---|---|---|---|---|---|
| **follower-crash** — SIGKILL one follower that is running workloads | n/a (leader survives) | 1896 ms | **2471 ms** | 2546 ms | 6.0 avg | 99.28% |
| **leader-crash** — SIGKILL the Raft leader (control plane + its workloads) | 568 ms | 2595 ms | **3187 ms** | 3207 ms | 5.8 avg | 99.15% |
| **leader+follower-crash** — SIGKILL the leader and one follower: 2 of 5 nodes | 554 ms | 2582 ms | **3205 ms** | 3279 ms | 17.4 avg | 97.36% |

### Where the time goes

Recovery ≈ *failure detection* (bounded by `--node-timeout`, plus an election if the leader died, because a new leader gives every node a fresh timeout before judging it) + *rescheduling* (one Raft round trip) + *task start* (one heartbeat for the agent to learn about the task, the runtime start, one heartbeat to report it running). Detection dominates by design: declaring a node dead too eagerly causes needless churn on a slow network. Lower `--node-timeout` trades false positives for faster healing.
